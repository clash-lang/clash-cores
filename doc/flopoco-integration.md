# FloPoCo Integration in Clash: Design and Analysis

## 1. Design and Reasoning

The goal of the FloPoCo integration in Clash is to leverage the highly optimized arithmetic operators generated by FloPoCo (Floating-Point Cores) directly within Clash designs. FloPoCo generates VHDL code for specific operators (e.g., floating-point adders, multipliers, exponentials) tailored to target FPGA architectures and frequency constraints.

### 1.1. Core Components

The integration is built upon four main components:

1.  **Execution (`FloPoCoCall.hs`)**:
    -   Handles the invocation of the external `flopoco` binary.
    -   Supports both Linux (direct execution) and Windows (via WSL).
    -   Captures standard output and error streams to retrieve the generated VHDL and any status messages.

2.  **Parsing (`Lexer.hs`)**:
    -   Analyzes the VHDL output generated by FloPoCo.
    -   Extracts critical metadata required for Clash integration:
        -   **Entity Name**: The name of the generated VHDL entity.
        -   **Ports**: Input and output signal names.
        -   **Pipeline Depth**: The latency of the operator, which is crucial for correct scheduling in Clash.
        -   **Frequency**: The target frequency used for generation.
    -   Relies on parsing specific comments and entity declarations in the VHDL output.

3.  **Data Structure (`InfoEn.hs`)**:
    -   Defines the `InfoEntity` data type, which serves as the intermediate representation for the extracted metadata.
    -   Stores `name`, `freq`, `pipedep`, `insig` (input signals), and `outsig` (output signals).

4.  **Code Generation (`GenTemDSL.hs`)**:
    -   Utilizes Template Haskell (TH) to automate the creation of Clash boilerplate.
    -   **`genBlackBox`**: The primary entry point. It takes an `InfoEntity` (usually constructed by calling FloPoCo via TH) and generates:
        -   **`BlackBoxFunction`**: Defines how the component is instantiated in the generated HDL.
        -   **`TemplateFunction`**: The logic for the blackbox template.
        -   **`Primitive`**: The `{-# ANN ... #-}` annotation that links the Haskell function to the BlackBox.
    -   This automation allows users to define a Haskell wrapper and immediately have a synthesizable implementation backed by FloPoCo.

### 1.2. Workflow

The typical workflow for a user is:

1.  **Define Wrapper**: Create a Clash function signature that matches the expected FloPoCo operator (e.g., `plusFloatExample`).
2.  **Generate Info**: Use a TH splice to call FloPoCo and parse the result into an `InfoEntity`.
    ```haskell
    infoEnPlusExample = $(genFloPoCoInfoEntity "flopoco" ["FPAdd", ...] "output.vhdl")
    ```
3.  **Generate BlackBox**: Use another TH splice to generate the Clash BlackBox infrastructure.
    ```haskell
    $(genBlackBox infoEnPlusExample)
    ```
4.  **Annotate**: Attach the generated primitive to the wrapper function.
    ```haskell
    {-# ANN plusFloatExample (flopocoPrim 'plusFloatExample 'plusFloatBBF) #-}
    ```

## 2. Current State

The current implementation provides a functional bridge between Clash and FloPoCo for specific use cases.

-   **Supported Operators**: The infrastructure is generic enough to support various FloPoCo operators, provided they follow the expected input/output naming conventions or can be parsed correctly. Examples exist for `FPAdd`, `FPMult` (via FMA), `FPExp`, and even a `VGAController`.
-   **Platform Support**: Explicit handling for Linux and Windows (WSL) suggests cross-platform intent.
-   **Automation**: The Template Haskell macros significantly reduce the boilerplate required to add new operators.
-   **Dependencies**: The system assumes the `flopoco` binary is installed and accessible.

## 3. Analysis of Potential Problems

While functional, the current design has several potential fragility points and limitations:

### 3.1. Parsing Fragility (`Lexer.hs`)
-   **Ad-hoc Parsing**: The parser relies on `words`, `lines`, and specific string matching (e.g., looking for "Input", "Output", "Pipeline" in comments).
-   **Format Dependence**: If FloPoCo changes its comment format or VHDL generation style (which can happen between versions), the parser will likely fail.
-   **Robustness**: The parsing logic might be brittle when facing unexpected whitespace or VHDL constructs not anticipated by the current logic.

### 3.2. External Dependency Management
-   **Binary Requirement**: Users must have `flopoco` installed. There is no version check or compatibility enforcement, which could lead to subtle bugs if the installed version differs from what the code expects.
-   **Path Management**: The examples often use hardcoded paths or assume `flopoco` is in the system PATH.

### 3.3. Error Handling
-   **Opaque Failures**: If FloPoCo fails or produces unexpected output, the error reporting might be limited to printing the stdout/stderr. The TH splices might fail with cryptic messages if the `InfoEntity` cannot be constructed.
-   **Pipeline Depth Mismatch**: If the parsed pipeline depth is incorrect, the Clash simulation might diverge from the hardware behavior, or timing closure might fail.

### 3.4. Integration Complexity
-   **Manual Steps**: Users still need to manually define the Haskell type signature and ensure it matches the FloPoCo operator's interface. Mismatches in bit widths or argument order are not automatically detected until later stages or runtime.
-   **BlackBox Overhead**: The generated BlackBox code is quite verbose and relies on string manipulation of signal names, which can be error-prone.

### 3.5. Scalability
-   **Single File Generation**: The current approach seems to generate one VHDL file per operator. Managing a large number of unique FloPoCo operators might clutter the project or build artifacts.

## 4. Code Quality and Testing Analysis

### 4.1. Code Quality
-   **Dependency Management**: The project uses Nix (`shell.nix`, `default.nix`) which ensures a reproducible build environment for Haskell dependencies. However, the **external dependency on `flopoco` is NOT managed by Nix**. Users must manually install `flopoco` and ensure it is in their PATH or provide the path explicitly. This breaks the hermeticity that Nix usually provides.
-   **Haskell Code**: The code makes heavy use of Template Haskell (`GenTemDSL.hs`), which is powerful but can be difficult to debug and maintain. The parsing logic in `Lexer.hs` is relatively primitive and lacks robust error reporting.

### 4.2. Testing Status
-   **Existing Tests**: There are **NO automated tests** for the FloPoCo integration in the current codebase.
    -   The `test/unit-tests.hs` suite covers other cores (Xilinx, Lattice, etc.) but has no entries for `ClashFloPoCo`.
    -   The `hdl-tests/Main.hs` suite, which tests HDL generation, also excludes FloPoCo.
-   **Verification Gap**: The lack of tests means that:
    1.  There is no guarantee that the `flopoco` binary is correctly invoked or that its output is correctly parsed.
    2.  There is no regression testing if the `flopoco` version changes.
    3.  The generated BlackBoxes are not verified against their Haskell behavioral models.

### 4.3. Simulation Behavior
-   **Behavioral Model**: In Clash simulation (Haskell execution), the FloPoCo wrappers behave exactly like standard Haskell functions.
    -   Example: `plusFloatExample` uses `liftA2 (+) a b`.
    -   This means simulation uses the host machine's floating-point implementation (typically IEEE 754 via GHC).
-   **Discrepancy Risk**: FloPoCo generates hardware operators that may have specific characteristics (e.g., custom precision, specific rounding modes, or optimizations that deviate slightly from standard IEEE 754).
    -   **Risk**: If the FloPoCo operator behaves differently from the Haskell `Float` implementation, the **simulation will NOT match the hardware**.
    -   **Mitigation**: Currently, there is no mechanism to verify bit-accurate correspondence between the Haskell model and the generated VHDL. Users must assume the FloPoCo operator implements the exact same standard as GHC's `Float`.
